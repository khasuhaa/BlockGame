# BlockGame

A 2D block-based game engine in C (raylib). See `README.md` for what the game does and how to build it.

## Quick guide: read this before adding anything

A checklist for a new session. The sections after it give the reasons.

**Before starting**

- `git fetch origin`, then `git status`. The owner edits files between sessions (recipes, the plans in `ModDescriptions/`, sometimes data). An uncommitted change that is not yours is theirs: do not revert it and do not commit it without asking. If it breaks a test, say so and ask.
- `saves/` is the owner's real worlds and is not in git. Only ever read it. Never write there from a test or a script; tests write under `build/`.
- Run `arch -arm64 make all test` first, so that you know it passed before you touched anything.

**Where a new thing goes**

| Adding | Do this |
| --- | --- |
| A block, item, recipe, creature, tree, ore vein | Data only: `data/*.json` and a texture. No C. |
| Something no existing field can express | A new field: declare it in `src/content.h`, read it in `src/content.c` with a default that leaves old data working and an error that names the file, then write the engine against the field. |
| Something that belongs to a mod | The mod's own files under `mods/<name>/`. If it needs the engine to do something new, that is a new field the base game could use too. Never `if (mod is on)`. |
| A new kind of saved state | Bump `SAVE_VERSION` in `src/save.c` and keep every older version loading (see below). |
| Interface text | A control's name and nothing else; explanations go in `README.md`. Check it fits at 1280x720. |
| A big feature or a big mod | A plan first, in `ModDescriptions/<Name>.txt`, with the open questions at the top; commit it and wait for the owner's answers. Afterwards append what was decided, what was built and what was not. |

**Every time, without being asked**

1. **An item needs a `"category"` and a `"price"`**, or the game will not start. That includes the item that places a new block, and each tier of a bench.
2. **A block that holds things** (`"storage"`) needs its item to have `"container": {"slots": N}`, or its contents are lost when it is picked up.
3. **Add or change a test** in `tests/test_game.c` for each rule. When shipped recipes change, fix the counts in `test_shipped_recipes`; when a mod's content changes, the counts in its `test_*_mod`. Leave `tests/legacy/` alone.
4. **Regenerate `obtainment.txt`** when recipes, drops or world generation change: `python3 tools/obtain.py .`
5. **A new way of getting an item** (a new kind of drop, loot or reward) needs a line in `src/guide.c`, or the recipe book says it cannot be got.
6. **Update `README.md`** (what it does, for a player) and this file (what a future session must know).
7. **Check the owner's saves still load** after any change to `src/save.c` or to a saved structure, by loading each `saves/*.world` in a throwaway program. Read only.
8. **A new creature must be cageable**: run `python3 tools/caged_art.py .` after adding one (and after any mod's generator), which adds its `caged_<name>` item, icon and `"caged"`. `test_all_caged` fails for a creature without.
9. **Nothing but benches at the workbench.** A new recipe goes to the bench that suits what it makes; `test_workbench_only` fails otherwise.
10. **Rerun `python3 tools/quests.py .`** after anything that changes what a mod or the game has (a generator, new benches, creatures, recipes): it rewrites every `quests.json` from the data. A quest that names something gone stops the game at startup, naming the quest.
11. **Commit and push** each finished change, with a short message that says what changed. No `Co-authored-by` or tool attribution in commit messages. Never rewrite history.

**Things that have gone wrong before**

- **The art is 16x16 pixels drawn double** (32x32 files for blocks and creatures; item icons are 48x48 - a block's icon is its 32x32 texture pasted at 8,8). Single-pixel detail at 32x32 looks out of place and was rejected. Use the palettes of the existing textures; `tools/bench_art.py` shows the manner.
- **Ids change from run to run.** Anything saved that names a block, item or recipe has to be translated on load. Blocks, items and creatures are (by name tables). Recipe positions are not: a machine's chosen recipe (`Storage.recipe`) and a door's kept look are only checked for sense after loading.
- **The tests also run at the old pace, without fog, and letting characters drop.** The same wrapper puts step times back to 0.12 / 0.16 / 0.22 (walk / climb / crawl) and `max_drop` to 0 (`test_no_dropping` has the shipped rule), and `game_init` is wrapped to turn the fog of war off, because the tests put characters down anywhere and click on what was never uncovered. `test_pace_and_flight` restores the shipped times; `test_fog` makes its world with `(game_init)`.
- **A step that is only a fall is filtered out in one place**: `drops_too_far` in `src/game.c`, applied by `list_moves` (what a route may use) and `key_step` (what the keys ask for). A new kind of step goes into `every_move` / `key_step_any` and is filtered with the rest.
- **The world is drawn in depth, by `src/world3d.c`.** The world pass in `session_draw` runs between `world3d_begin` and `world3d_end`: a real perspective camera looking at the flat picture, which is the front of the scene (z 0). Three rules keep it working:
  - Every texture in `src/assets.c` is drawn through `world3d_texture`, never `DrawTexturePro`. It draws flat unless a depth has been set (`world3d_solid` for a block or a picture with thickness, `world3d_plane` for a flat picture further back), and the code that sets one puts it back with `world3d_flat`. `block_depth` in `src/main.c` decides for tiles; the depths are the `Z_` constants there. The kinds of model are in `src/world3d.h` (material, box, built frame, body, panel, crossed plant): a new tile gets one from what it is - a crossed plant if it is sown or grows; a built model only if it is furniture (a bench, storage, a bed, a lamp, a column or stairs); a block if its picture fills its square; otherwise a panel one pixel deep, as creatures are - and `"model"` in the data overrides. The owner wants built models only for blocks and furniture. The owner likes things that are pictures rather than furniture - portals, eggs - as `"model": "panel"`, one pixel deep: prefer that for a new thing of that sort over a built-up model. Look at a new non-block tile in the debug world before shipping it. A solid tile that is a thing and not material (`stands_alone`) is one block deep, and the backwall is drawn behind it. Any square that `world_is_solid` says stops a character is drawn the full depth, front to back, even when it is one square of a background thing (a portal's `solid_foot`): keep that so when adding another way for a square to be solid.
  - Plain raylib drawing (rectangles, text, lines) inside the pass lies on the front of the scene, exactly where it would in 2D; wrap it in `world3d_push(z)` / `world3d_pop()` to put it further back.
  - What is under the cursor is found in depth (`tile_at_screen`, `world_at`): do not turn the mouse into a square by dividing by the zoom.
  Interface drawn outside the pass is untouched. The darkness and fog are laid over the front with the depth test off (weighed against the block faces they lie on, they flicker as the zoom changes), and it is switched back on for what glows, which is drawn again where it stands. The view's origin is kept to thirty-seconds of a pixel so that neighbouring edges are the very same numbers: do not place world drawing by any other arithmetic than `origin + whole pixels`, or hairlines open between blocks while zooming.
- **A world can have other places under it** (`World.regions`, `src/world.c`): a dimension is a stretch of rows appended below the rows the world began with, never a second `World`. So everything that is per-world - creatures, water, machines, saves - covers them with no further work, and existing coordinates never move. What must know about them: anything that looks for the sky scans up to `world_sky_top`, not to row 0 (`light_compute`, `game_exposed`, the generators in `src/power.c`); the kind of country is `world_biome_at(w, x, y)` (the plain `world_biome` is only the world as it began); random events are shared out a place at a time in `game_tick`; and only the place the view is in is drawn (`view_rows` in `src/main.c`). `world_add_region` makes the grid bigger, so the game's own per-square buffers and the planning copy have to follow: always go through `game_enter_dimension`. A new per-square array in `Game` or `World` must be grown in `game_world_grew` / `world_add_region`.
- **Villages are made last, from numbers of their own** (`place_villages` in `src/world.c`, a stream seeded apart from the world's): with no villages in the data nothing is drawn, and with them the rest of the world is what it would have been. `test_rags_mod` checks that. A structure square with no backwall of its own keeps the world's - otherwise a market in a cave has sky behind it.
- **Home world generation must not see dimension content.** Veins, cave decorations and biomes with a `dimension` are skipped by the world's own generator before any random number is drawn (`place_veins`, `place_decor`, `assign_biomes`): keep it so, or every world changes. A dimension draws from a stream of its own, seeded from the world's seed and its name.
- **A mod adds bench levels with `"extends"`, never by redefining the top tier** (`extend_benches` in `src/content.c`, run on every load so that it comes out the same whatever order mods load in). Recipes for such a level say `"at": "<block>"` as well as `"bench"`, and get the level worked out.
- **The character's poses are all eased** (`draw_player` in `src/main.c`): a state works out a target pose and the drawn one moves toward it. Sleeping, meditating and dying are states like any other there - do not draw a state directly and return, or it will snap.
- **Flying is swimming in air.** `World.aloft` is set by the game for the character in hand (`set_aloft` in `src/game.c`) and makes `buoyed` true in open air; everything that plans a move goes through that. A new entry point that plans or moves must call `set_aloft` first.
- **Pace comes from happiness alone** (`game_pace` in `src/game.c`): the average of energy, hunger and the environment score, capped by health - and past full, a fifth faster, when all three are kept past full and health is whole. Food is `cooked` (and can keep hunger past full) if a recipe makes it, unless its data says; that is worked out in `validate` in `src/content.c`. Anything new that should slow a character goes into `happiness_of`, not into the step timings. The tests' wrapper zeroes `happy_slow` as well, so that hungry or hurt test characters keep their old timings; `test_environment` restores it.
- **The tests run with the weather off.** `tests/test_game.c` wraps `content_load` to zero `env_fall_ticks`, because its characters stand about with nothing on for thousands of ticks; `test_environment` puts the shipped value back. A new test that needs the environment score does the same. Anything wearable needs a `"warmth"` (its share of the score it keeps), or it only counts as "something on".
- **What runs on rails is not blocks.** Vehicles are `Game.vehicles` (`src/train.c`), saved whole from version 31, each naming its item; their fuel and cargo are containers of the inventory, which is why the tests' `clear_inventory` must not be called once a vehicle is down (the railway test empties the bar by hand). Coupling is touching: there is no link to keep. A character riding has `Game.ride` set and is moved by the vehicle; `game_click_tile`, `game_queue_action` and `start_next_activity` all refuse while it is. A new kind of vehicle is an item with `"vehicle"` and a picture - no C.
- **`World.meta` is one number per square, shared**: tulip colours, ice, a lift motor's power flag, a sign's text, a door's look. A new use must clear it when the block goes (`world_set_at`) and must not collide with a block that already uses it in the other layer.
- **`Storage` is written to saves raw.** Adding a field to it (or to `Vitals`, `Inventory`, `Drop`, `Mob`) changes the file layout: add a `StorageNN` copy of the old layout and a reader for it, as `read_storages_26` does.
- **What is worn is more than armour.** Anything that asks what a character has on - speed, protection, warmth and the rest - goes through `game_boons` (armour, then the relic slots, then what enough of a set gives). The relic slots are a container of the inventory marked `CONTAINER_RELICS`, found by `game_relic_box`; the tests' `clear_inventory` frees it like any other, and `game_relic_box` makes another. A loot pool may name biomes the game has not got (another mod's): they are left out, not an error - that is how one mod's finds reach another's biomes without depending on it.
- **Fruit hangs at the tree's depth, not the character's** (`Z_MID` in the drops' drawing in `src/main.c`), is picked by walking through its square (`collect_nearby` in `src/game.c`), and a click looks for it at that depth. Something falling is caught as it passes, after a fifth of the usual wait.
- **A wall picture must tile**: a frame all round each square doubles every beam where two meet. Put a beam on two sides only (see `wall()` in `tools/mod_rags_to_riches.py`). A window underground shows sky: the cave style has none.
- **A basket goes to the bar first** (`add_stack_rest` in `src/inventory.c`): an empty bar slot, then the slot of something that is not a basket (which goes inside it), and only then inside another basket. The owner asked for this.
- **The bare hand is a selection, not a slot**: `sel_inner == SEL_HAND` (`inventory_hand`), with `sel_slot` left pointing at a real slot so that nothing indexes out of the bar. `inventory_selected` returns an empty stack then, and `inventory_tool_speed` no tool. Anything new that picks a tool or an item for the character must go through those two.
- **A click means one thing.** `game_click_tile` and the chain in `handle_input` (`src/main.c`) decide by what is in hand and what is under the cursor, in order. A new use of a click goes in that chain at the right place, and the test should drive it through the click, not through `game_queue_action` - a rule that works when queued directly can still be unreachable by clicking.
- **The tests' `clear_inventory` frees every container**, including those of chests and machines already set down in the test world. Set bar slots directly when the test has machines in it.
- **World generation shares one random stream.** Drawing a number in a new place changes every world made afterwards from the same seed. Guard new draws so that with the feature off (a rate of 0, a list that is empty) none is made - the legacy tests rely on it.
- **Background blocks behind a solid block are hidden**: not drawn, not opened (`usable_at`), not glowing. Wire is the exception: it is drawn over the block and comes off first.
- **Cave biomes use no random numbers from the world's run**: where they are and what grows in them comes from hashes of the seed and the square (`dress_caves`). Keep it so, or every world's trees and plants shift.
- **Biomes are placed by rectangles of heat and dryness**, and where two overlap the one loaded later wins - mods load in order of name. A new biome takes its rectangle out of whatever was there, so check it against every other mod's rectangles (they are in each mod's `worldgen.json`) and do not overlap them. A biome's `"soil"` is a block deep at the edge of its country and deepens inward; its `"under"` rock comes in only at the very heart, which a small rectangle seldom has - so a rock that is meant to be found goes in as the soil, or in veins as well.
- **Two mods that define the same name cannot both be on**, and both turn off. Give a mod's things names of its own; only redefine a base thing (as both Magic and Mayhem and Industry redefine `workbench_4`) when you accept that it will clash with any other mod that does.
- **A new field that is an index needs its "none" set for entry 0 too.** `leads_dim` is -1 for no dimension; left at 0 for `TILE_AIR` it made every empty square something to open, and half the tests failed. Set such a field where the definition is read *and* check what the zeroed first entry gets (`validate` in `src/content.c` runs over every tile, from 0).
- **In `src/content.c`, set a definition's fields after its `memset`, not before.** A cave decoration's `dimension` was set and then wiped, which quietly put another place's decorations into every new world.
- **Weather made to order and creatures held still are not saved** (`Game.weather_until`, `Game.held_until`): a rain bottle's rain stops at a reload. Say so if it comes to matter.
- **Check a mod's names against every other mod's before settling them** (the per-mod tests call `mods_conflict` against all the others). Dimensions first clashed with Explorer's Delight over `mycelium`, `glow_vine` and `willow_catkin`. A search-and-replace to rename must not touch the other mod's tests.
- **A copied definition copies everything.** A generator that makes an item from one of the game's must keep only how it looks and is held, or the copy also places the original's block, plants its tree or is its food (see `item()` in `tools/mod_dimensions.py`).
- **A pack on the back is part of the body, not a picture over it.** An item with `"pack": true` gets a box on the back of the torso, drawn from 32,0 of its worn picture, and the flames under a jetpack are two more boxes drawn from 52,0 (`playermodel_draw` in `src/playermodel.c`; `tools/worn_art.py` paints both). The flames used to be flat rectangles drawn after the body and so over it: anything that belongs behind or beside the body goes into the model.
- **The view follows `Game.travels`.** Anything that moves a character from one place to another bumps it, and `update_camera` then puts the view on them and follows, whatever it was doing (zooming lets go of following, which is how a portal seemed not to take the view along). The view is also kept inside the rows of the place it is in.
- **A recoloured picture with two materials needs two ramps** (`'ore'` in `tools/mod_dimensions.py`: the coloured part by one, the grey by another). Recolouring a portal all one way lost its frame and looked broken.
- **Never cast the wheel to a whole number where it is read.** A slow scroll on a trackpad comes as fractions of a step, and `(int)GetMouseWheelMove()` threw every one away, so the mod list would not scroll slowly. A list that moves by rows keeps the fraction until it adds up (`wheel_rows` in `src/menu.c`); a list that moves by pixels multiplies the float.
- **A bench menu must take any number of recipes.** The list is a strip that scrolls sideways; past 60 recipes it is two rows deep and past 150 three (`list_rows` / `LIST_SHIFT` in `src/benchui.c`, set beside `note_rows`: everything below the list is moved down by it). Seeker of the Dao's pill furnace has about 350. Looked at with nothing chosen; not with a recipe chosen in a three-row menu.
- **A bench menu must take a recipe of any size.** What a recipe needs is set out in rows of four, as many rows as it takes, and the menu grows (`note_rows` / `extra_rows` in `src/benchui.c`: every `menu_rect` in a frame has to see the same number). Do not go back to one line that shrinks. The **Upgrade** button's cost is still one line and is cramped for a cost of several things: the owner has been told, and has not asked for it to change.
- **Money is shown in the biggest coins that make it up**, never as one number of the smallest: `trade_coins` / `trade_price_text` in `src/trade.c`, `draw_price` in `src/tradeui.c`. Use them wherever a price is shown.
- **Big worlds with every place open are heavy.** The route-finding buffers and each character's steps are sized by the whole grid, and the planning copy of the world is copied whole on a click: on a world 6,144 wide with three dimensions that is some hundreds of megabytes and about 60 MB a click. Not measured in play. If it is slow, bound the search and the copy to the place the character is in.
- **Tools that do not survive the session**: scratch scripts and screenshot harnesses live outside the repository and are gone next time. Anything worth keeping goes in `tools/`.

**Checking what cannot be tested**

Rendering and menus have no tests. To look at them, write a small C file that does `#define main real_main`, `#include "main.c"`, `#undef main`, then its own `main` that loads content, sets a scene up, calls `session_draw` and `TakeScreenshot` - built against every `src/*.c` but `main.c`, and run from the repository root. Keep such files out of the repository (raylib's `TakeScreenshot` writes into the directory the program is run from, whatever path it is given: move the picture out of the repository root afterwards). Say plainly in the report what was checked this way and what was not.

**`tools/`** (each takes the repository root as its argument; rerunning one with nothing changed changes nothing)

- `obtain.py` - writes `obtainment.txt` from the data.
- `quests.py` - writes `data/quests.json` and each mod's `quests.json` (a tab each: its benches, a spread of what it makes from first to last, its creatures, its places; chapters of eight), and `mods/questbook` itself. A quest's name is made from what it is about, so a save still knows it when the list around it changes. Quotas, and which mods count as big, are at the top of it.
- `prices.py` - reprices items from their recipes. It overwrites prices in `data/items.json`: run it on purpose, not as routine.
- `mod_magic_mayhem.py`, `mod_industry.py`, `mod_digital_storage.py`, `mod_culinary_delights.py`, `mod_explorers_delight.py`, `mod_discovery_road.py`, `mod_alchemie.py`, `mod_dimensions.py`, `mod_rags_to_riches.py`, `mod_machinations.py`, `mod_potioncraft.py`, `mod_seeker_of_the_dao.py`, `mod_beyond_the_sky.py`, `mod_plunder_and_thunder.py`, `mod_dungeoneering.py` - each wrote one mod's data files and textures. Either edit the script and rerun it, or edit the mod's files by hand and stop using the script: not both, or the script will undo the hand edits.
- `bench_art.py` - drew the bench textures in `data/textures/tiles/`.
- `trade_tiers.py` - applies the owner's `TradeTiers.txt` to `data/items.json` (category, tier, order; everything it leaves out to one of the dev portal's categories: `benches`, `portals`, `creatures`, `special`) and writes `TradeObtainment.txt`. How that document is read is a table in the script, set down by hand: change it when the document changes.
- `stair_column_art.py` - draws every `*_column` and `*_stairs` block in the game and in each mod, and its icon, in the manner of what it is made of: stone, plaster, wood, brick, metal, carbon fibre, gem or glass (told from the name; `KINDS` in the script). The owner asked for this: a gem column must not be an iron column in another colour, though two gems may differ only in colour. Colours are kept in `tools/stair_column_palettes.json`, one line a material, so rerunning changes nothing: edit a line there to recolour or to move a material to another family. Run it after adding a column or stairs and after any mod generator that makes them (`mod_dimensions.py` runs it itself). A new family is a new branch in `column()` and `stairs()`.
- `caged_art.py` - for every creature in the game and in each mod with no `"caged"` item: adds the item (to that directory's `items.json`), names it on the creature, and draws the icon - the creature behind the game's own bars. Run after adding a creature and after any mod's generator; `mod_dimensions.py` runs it itself.
- `train_art.py` - draws the rail, the ramp, the station board, the four vehicles (`data/textures/vehicles/`) and their icons. A vehicle's bottom five rows are left clear so that its wheels stand on the rail; its windows are clear so that riders show through.
- `portal_art.py` - draws every portal's blocks and icons (the arch, its spiral, the tier's stone in the keystone). A new kind of portal is a new line at the bottom of it.
- `worn_art.py` - draws the character's skin (`data/textures/player/base.png`) and, for every item with an `"equip"` slot in the game and in each mod, what it looks like worn (`textures/worn/<name>.png`), and sets the item's `"worn"`. **Run it after adding anything that can be worn**; `test_worn` fails for an item without a picture. Give a new kind of clothing its look there, by a word in its name.

## What the owner has asked for, and holds to

Said in so many words over the sessions; do not make them say it again.

- **The workbench makes benches, machines and blocks to trade at, and nothing else.** Said twice.
- **Mods' things go in the trade's own categories**, by what they are. A section for each mod was built and taken back out: a mod the size of Dimensions swamps one list. Benches, portals and creatures are in the dev portal's own categories (`benches`, `portals`, `creatures`, `special`), which were split out of one bloated `special`.
- **Every creature can be caged**, in the game and in every mod.
- **Prices read as coins**: 100 copper is a gold, 100 gold a platinum; 15,500 is "1 platinum, 55 gold".
- **Menus must cope with any amount of content**: nothing runs off the screen, however big a recipe or however many mods.
- **Mods are meant to be big**, and are asked for as such; crafting trees for the great makings should be ten and more makings deep. A plan comes first for anything large (see the table above), and the owner answers its questions.
- **Places should be worth looking at.** Bare generated terrain was called disappointing: a new place wants shapes of its own, things standing in it, things that glow, and something to find. The generators have data for that (`"spikes"`, `"treasure"`, `"geodes"`, island kinds in `region_island`): use it, and look at a wide screenshot before calling a place done.
- **Tapping a character's icon brings the view back to them**, as well as opening their panel.
- **Things of different stuff should not be recolours of one picture.** Said of columns and stairs (see `tools/stair_column_art.py`); take it as the rule for any family of look-alike blocks a mod adds.
- **Art**: 16 by 16 drawn double, the game's own palettes; things that are pictures rather than furniture one pixel deep. Recolouring the game's own art for a mod (as `tools/mod_dimensions.py` does) has not been objected to, but it was reported as a weakness: fresh drawing is the better answer when there is time.
- **Report what was not built.** When a plan is cut down, say so in the report, in `README.md` and at the end of the plan.
- `TradeTiers.txt` is the owner's own file and has never been committed: they were asked, and have not said. Leave it untracked.

## Core directive: keep everything data driven

The goal is mod support. Anything a mod might want to add or change must live in data, not in C.

**The engine knows what fields mean. It does not know any content by name.**

- Content is defined in `data/*.json` and drawn from `data/textures/`. The loader is `src/content.c`; the tables it fills are described in `src/content.h`.
- No block, item, recipe, tree, terrain feature or tuning number is written into the C code. There is no `TILE_DIRT`: code asks `tile_def(t)->solid`, or uses a tile that a data file named for that role (for example `content.worldgen.soil`).
- Ids are positions in the loaded tables and change from run to run. Never store or compare a literal id other than `TILE_AIR` and `ITEM_NONE` (both 0). Save files record names, not ids.
- `content_load` is additive: loading a second directory adds new definitions and replaces ones with the same name. Keep it that way; it is how mods will load.

### When adding a feature

1. Decide what a modder would want to vary, and put that in a data file: a new field on an existing definition, or a new kind of definition.
2. Teach `src/content.c` to read it, with a sensible default so existing data files keep working, and an error message that names the file and the problem when the data is wrong.
3. Write the engine code against the field, never against a specific block or item.
4. If the feature only makes sense for one piece of content, that is a sign the behaviour belongs in a data field (as `climbable`, `bench` and `front` are) rather than in a special case.

A new constant in C needs a reason it could not be data. Fixed sizes of saved structures (inventory slots, basket slots) and limits on table sizes are the accepted exceptions.

### Every item has a category and a price

Every item in the game except the coins belongs to a trade category and has a buying price. The dev portal lists them all by category; trade portals deal in the ones that are not barred. Whenever an item is added, removed or renamed:

- **Adding an item** (including the item that places a new bench or block, and each tier of one): give it a `"category"` from `data/trade.json` in `data/items.json`, and a `"price"` in copper coins that fits what it is made of (10 is the least). Add a new category to `data/trade.json` if none fits.
- **Removing an item:** take it out of `data/items.json` and out of anything that names it - recipes, upgrade costs, drops, starting items, currencies.
- Only currencies listed in `data/trade.json`, and items that are never held - ones that turn into crystals when picked up (`"crystals"`), or into a character when made (`"becomes_player"`) - may be left without a category.
- **The categories, tiers and order come from the owner's `TradeTiers.txt`**, applied to `data/items.json` by `tools/trade_tiers.py` (its `READ` table is that document, read by hand). A new base-game item the document names: add it to `READ` and rerun. One it does not name: `"category"` one of `benches`, `portals`, `creatures` or `special`, which only the dev portal lists (`"free_only"` in `data/trade.json`). Rerun the tool after adding items either way: it also moves items into the document's order and rewrites `TradeObtainment.txt`.
- A mod's item gives a `"category"` (the old names still work through `"also"` in `data/trade.json`) and may give a `"tier"`; with none it gets one from its price (`"tier_prices"`). Tiers run past the game's six: Dimensions' are VI to X, bought at the trade portal levels it adds, and the menu has numerals to X.
- Trade portals do not deal in things to trade at, in anything a recipe takes crystals to make, in anything of a `"free_only"` category, or in anything above the tier the portal has been raised to (`"trade_level"`). The first three are `trade_barred` in `src/trade.c`, worked out from the data: do not add a flag for them.
- The trade menu keeps a place for every item a portal could deal in, tier by tier and within a tier in the order `items.json` defines them, and shows a `?` until the item is found (`game_trade_listing` in `src/trade.c`). Do not filter or sort that list in the menu: found things must not move.
- Selling gives `"sell_share"` of the price. Do not add a recipe that turns coins into something worth more than the coins.

The loader enforces the category: an item with none that is neither a currency nor never held stops the game at startup, naming the item. Do not weaken that check to get a new item in; give the item a category.

### Mods

- A mod is a directory under `mods/` loaded on top of `data/` by `content_load` (see `src/mods.c`); the ones the game comes with are `mods/magic_mayhem` and `mods/industry`, each written out from its plan in `ModDescriptions/`, and `mods/digital_storage` (storage networks: `src/digital.c`, with the terminal's screen in `src/termui.c`), `mods/culinary_delights` (crops, trees, biomes and a kitchen) and `mods/explorers_delight` (biomes and building blocks), and `mods/discovery_road` (relics, relic slots, sets, and chests that hold what belongs to where they stand - which needed worn `"boons"`, `"sets"`, `"loot_pools"` and `{"area": true}` loot of the engine: `game_boons` and `game_area_find` in `src/game.c`; its relic identifier is an item that `"identifies"`, read by `draw_identified` in `src/main.c`), and `mods/alchemie` (benches that turn one thing into another; a recipe may have no inputs at all, as its Transmutation Table's have, and its Tome of Knowledge is an item that `"reveals_all"`) - the first data only; the second needed two things of the engine (seas chosen by climate, and `"cave_biomes"`, both in `src/world.c`). Everything a mod does it does through the data: if a mod needs the engine to do something new, that is a new field the base game could use as well, never a check for the mod.
- A mod's items follow the same rules as the game's: every one has a category and a price.
- **The workbench makes benches and nothing else** - benches, machines, and the blocks to trade at - in the game and in every mod (the owner has said so twice). Anything else goes to the bench that suits it: wood to the woodwork bench, stone to the builder's bench, parts to the craft or metalwork bench. `test_workbench_only` loads the game and each mod in turn and fails on any other workbench recipe. It is smaller than its plan: section 8 of the plan lists what was left out (weather of its own, mounts and taming, the airship and drill rig, timed effects, sky anchors and recall stones, built ruins), its recipes are about 200 a dimension against the game's 505, and it has never been played through - balance, prices and how often things turn up are guesses.

(3) a formation's heart is a bench with fuel (so it has a `Storage`); how far it is lit is kept in `Storage.work` and looked at every 10 ticks; herbs do NOT see formations - `world_qi` (which gates growth) knows only the world, `game_qi_at` adds formations for meditating; (8) a `void` dimension with `"structures"` gets a level island (`"void": {"length", "depth"}`); (10) the mod was first built at a third of its plan's size and the owner sent it back: it now has 588 blocks, 1,084 items, 1,149 recipes and 62 creatures, and section 12 of the plan says what is still short; (16) the owner then asked for every gap in the plan to be filled, and it was, each as a data field - `"formula"` on a recipe (made only where that item is in `Game.discovered`; `game_recipe_known`), `"comprehension"` and `"quickens": {"refines"}` on blocks, `"technique": {"element"}`, `"cast": {"blink"}`, `"natal"`, `"flight_qi"`, `"feeds"`, `"cages_kept"` on items, `"mount"`, `"strike"` on creatures, `"bars"`, `"wanders"` and the `"double"` pattern on formations, `"temper_qi"`, `"core"`, `"domain"`, `"soul"` on realms, `"manual_costs_stage"`, `"death_costs_qi"`, `"stars"` on a dimension, `"bestows_qi"` and `"needs_stage"` on a block, `"meditation": {"also"}`; (17) a learned technique is cast without its item: `cast_spell` allows what `dao_known_slot` finds, the one in hand is `game_technique_armed` and is looked at FIRST in `game_click_tile` and `game_click_mob`, and `cast_spell` itself pays (`wear_spell`) - do not pay again after calling it; (18) riding is `Game.mount` (not saved): the creature is pinned to its rider in `mobs_tick`, the pace is in `game_boons`; (19) the world asks the game for what formations add to qi through `World.qi_more`, set every tick in `dao_world_tick` - `game_qi_at` must not add it twice; (20) `world_qi` has a seed-noise term of 0 to 0.25: herb thresholds and tests are set with that in mind; (21) the technique row uses Shift and a number, fixed in `src/daoui.c`, not in the bindings table; (22) spirit sight is drawn in `session_draw` over the world from `view_tile_pos`, every other square, worked out afresh only when the view moves. (23) the owner asked for deeper crafting trees - 6+ makings in midgame, 10+ near the end, 15+ at the end - and the generator now ENFORCES it: near its end it adds each craft's intermediate things (the `# ---- long makings` section), rewrites the inputs of the recipes already made (`needs_also`), works out the fewest makings every finished thing takes (`steps`: what is dug, grown or dropped is 0; a recipe that takes its own output, a copy, does not count) and asserts the least for Core Formation (6), Divinity (10) and an immortal's (15). A new finished thing gets its components from that pass by its bench, category and tier - give it the right ones and nothing more is needed; a new SHORT way to a finished thing (a treasury, a drop, a conversion) will trip the assert, which is the point. `heaven_calling_talisman` is left out of the Dao-fruit rule on purpose: it is how the first heaven-tempered essence is got. (9) `worn_art.py`, run over the repository, redraws 28 worn pictures of `mods/dimensions` differently from what is committed - they were put back each time; do not commit that by accident.
- `mods/beyond_the_sky` (rockets, orbit, the Moon, the Belt, the red planet; what was asked and built in `ModDescriptions/BeyondTheSky.txt`) is written by `tools/mod_beyond_the_sky.py` (whose first 350 lines are the same drawing helpers as Seeker of the Dao's generator: change one, think of the other). Its engine half is small and all in data fields: (1) the `"surface"` generator (`region_surface` in `src/world.c`): terraced ground - level stretches are what `region_built` needs to stamp a structure - craters, a canyon, tubes whose floors are set to the biome's surface so that plants and treasure are found below too; (2) `"airless"`: `game_airless` makes the breath run down exactly as under water (same bar, same `lung` boon), and `game_aired` flood-fills the room a square is in (700 squares at most; a square with no wall-layer tile behind it is a hole) looking for a lit `"air"` block - worked out for the character every 10 ticks (`Game.air_tick`), on demand for a crop; (3) `"gravity"`: 0 sets `World.aloft`, less than 0.9 sets `World.glide`, both in `set_aloft` - which is called when a move is planned, not every tick; (4) rockets: a `"launch"` gate is open only with a stack of `"rocket"` blocks under it on a `"pad"` that adds up (`game_rocket_report`, used by `game_gate_open`, by `game_travel` which spends the stack and rolls the failure, and by the readout in `session_draw`); the capsule is an ordinary gate, so the one put down at the far end is the way home. A dimension may now list 24 structures and there is room for 128. The generator runs `worn_art.py`, `caged_art.py` and `stair_column_art.py`. It prints how many makings deep each tier's finished things are; it does not assert it.
- `mods/plunder_and_thunder` (ocean worlds, island towns, ships, boarding, buried treasure; plan, answers and what was left out in `ModDescriptions/PlunderAndThunder.txt`) is written by `tools/mod_plunder_and_thunder.py` (the same drawing helpers at its head as Seeker's and Beyond the Sky's generators), in three passes one after another in the file: the later ones change the earlier ones' recipes with `swap` and `also`, so read to the end before changing a ship's making. The engine half, all data fields: (1) `"ocean"` in `worldgen.json` (`ocean_levels` and `sink_wrecks` in `src/world.c`): the levels of a new world are remade as sea bed and islands from a stream of their own, so a world without it is what it was (`test_plunder_mod`, `test_dungeoneering_mod`, and `test_questbook` for every mod's quests checks); `"biomes"` there is what an island may be - one to an island, by a hash of the seed and where it is, at the end of `assign_biomes` - because climate rectangles left most islands as the base game's plains; `"wrecks"` are structures stamped on the deep sea bed and `"buried"` a block put under beaches. The structures are named, not indexed: they are read after the ocean is. (2) A ship is a creature that swims, with `"mount"`, and `"ship": {guns, range, wreck}`: ridden, her guns are the rider's attack (`game_attack_damage` / `game_attack_range`), a `strike` lands on her and not on the rider (`src/mob.c`), and dead she leaves her `wreck` block on the bottom - on top of a chest or a bench, in place of weed. Her item is her `"caged"` item, which is how she is launched and taken up. (3) `"boarding": {crew, count, captain, deck}` on a creature and `"boards"` on an item: `game_board` in `src/game.c` turns the ship into a deck of blocks at the waterline with her crew on it. It happens at the click, when near enough, not through a queued action: ships do not stay where they were clicked. (4) `"treasure_map"` on an item (its meter is the column it points to, plus one; `game_treasure_column`) and `"buried_treasure"` on a block; the map's picture is drawn in `session_draw`. Things to keep: a creature with no `"ship"` has `gun_range` 0 - a default range once gave every creature guns; sea-bed and shore plants are `"biome_plants"` against the base `ocean` biome and the islands' own; `MAX_VILLAGE_KINDS` is 24 because this mod has ten kinds of town. It is smaller than its plan and unplayed: the README lists what was not built.
- `mods/questbook` is one line of rules (`"questbook": true`) and nothing else: the quests are the ENGINE's, read from a `quests.json` in the game's data and in any mod (`read_quests` in `src/content.c`, the last file read, so it may name anything of that mod's or the game's - not another mod's). That is the whole of how a mod uses it, and why a mod works the same with the book off: `game_quests_on` is false, nothing is tracked (`quests_tick`, `game_quest_killed` and the claims all return at once) and nothing is drawn. Tasks are `"have"`, `"kill"`, `"near"`, `"in"`, `"biome"`, `"stage"` and `"check"` (`game_quest_progress` in `src/game.c`); a new kind of task is a new `QUEST_` there, read in `read_quests`, said in `task_text` in `src/questui.c`. State is `Game.quest_state` / `quest_progress`, by quest index, for the world (not per character) - looked at for whoever is being played, every 20 ticks. "Have" looks at what is held now and latches; it does not use `Game.discovered`, which a Tome of Knowledge fills at a stroke. A quest must come after everything it needs in its file (`test_questbook` checks: it is how there is always a way through). There is room for 2,048 quests and 24 tabs; every mod on at once is 966 and 17. The book is a list, not a tree; the screen was looked at with four tabs, not with seventeen.
- `mods/dungeoneering` (ten dungeons, a gate, a forge, loot with numbers of its own; plan, answers and what was left out in `ModDescriptions/Dungeoneering.txt`) is written by `tools/mod_dungeoneering.py` from `tools/dungeoneering_loot.csv` - the first ten dungeons of a list the owner supplied (their own copy is in the repository root, untracked, like `TradeTiers.txt`: leave it so). The engine half, all data fields: (1) **rolled things**: an item with `"rolled": {power, upgrades, gain, health, health_gain, class}` and a `"grade"`. How one fell is its METER, which is 16 bits and no more: base and count of upgrades each as one of 21 hundredths, and how many goes at upgrading it has had (`game_roll` in `src/game.c` reads it; 0 is "not fallen yet", shown as the middle). Upgrades are counted in goes (`"upgrade_steps"`, 50) because the list's counts run to 80,000 and would not fit. A thing is rolled wherever it turns up, by `roll_everything` every 20 ticks - there is no path to remember to roll on. Each rolled thing is a CONTAINER (that is how meters are kept) and there are 1,024 of those in a world: a hoard of several hundred will fill them; nothing checks. (2) **blows as numbers**: `"power"` in a creature's `"sting"` or `"strike"`, taken from `game_max_health` (`"combat": {"health"}` and the health of what is worn) by `game_blow`; a creature with a power stings without poisoning. A weapon's power and what is worn replace `damage` in `game_attack_damage`. (3) **the place**: one dimension whose `"generator"` is `"dungeon"`, solid until `world_dungeon_build` makes a run in it (`"dungeons"` in `worldgen.json`: blocks, creatures by name with the boss last, loot with a `rank`); `game_dungeon_enter` empties it of creatures, storages and drops and builds again from a new seed, so a run is new each time though the place is kept and saved. Which dungeon and how hard is one number in `World.meta` on the place's top row at the spawn column (`world_dungeon_run`): nothing about a run is kept in `Game`, which is why saving needed no change. Creatures are not there until somebody is near: the builder leaves `"dungeon_spawn"` marks, and `dungeon_tick` turns those within 26 columns and before the first shut door into creatures (a creature far from everybody is taken away by `mobs_tick`, which is why they are not all made at once). A `"dungeon_door"` opens when no mark and no creature not owned is left nearer the start than it is. (4) the gate and the forge are benches whose menus are their own (`src/dungeonui.c`; `is_trade` in `src/benchui.c` keeps the bench menu out of the way); the gate's reach is the level of the nearest bench of the kind it names (`"dungeon_gate": {"beside": "portal"}`), so it follows whatever raises the portal, this mod's tiers or another's. (5) the way out is a tile that `"leads_to"` the place and is a `"dungeon_exit"`: `game_travel` sends it to `game_dungeon_leave` before anything else. (6) difficulties and grades are `"dungeons"` in `rules.json`. Things to know: `MAX_ITEMS` went from 4,096 to 8,192 for this (every mod together was already past it); with this mod's 60 creatures, every mod on at once is past `MAX_MOB_KINDS` (192), which cannot be raised past 255; the numbers each dungeon's creatures have are worked out in the generator from the loot of the dungeon before (it prints them) and have never been played against; a storage block must have an item to drop even if it can never be taken up, so the reward chest has one.
- `mods/potioncraft` (herbs, cauldrons, potions; plan and answers in `ModDescriptions/Alchemy.txt`) is written by `tools/mod_potioncraft.py`. The engine half is in the base game for any mod to use: something taken can put a character under an **effect** - boons for so many ticks, or for good (`Game.effects`, `take_effect` and `game_boons` in `src/game.c`; saved by item name from version 36). An effect is just a third source of boons beside what is worn and what a set gives: a new thing a potion should do is a new field of `Boons` read in `read_boons`, added up in `add_boons`, and asked for where it matters. A flask is a spell with one use (`"cast"`), so a new thing to throw is a new `cast_` field done in `cast_spell`, and it must be named in the click rule in `game_click_tile` that says which spells are aimed at a square. None of the game's own food has an effect: the owner said not yet. A recipe that names another mod's things is `"optional"`.
- `mods/rags_to_riches` (villages, villagers, trade only in villages at each village's own prices, specialities) is written by `tools/mod_rags_to_riches.py`: its buildings are the `BUILDINGS` table there, built once in each of the `STYLES`. A village is not saved anywhere: it is wherever a block with `"village"` stands (`game_village_at` in `src/trade.c`, which looks through the world again every 200 ticks), and its number - which its prices and specialities come from - is made from the world's seed and that block's place. Prices at a block are `game_trade_price` / `game_trade_sell_price`, never the plain `trade_price`, which is the usual price everywhere.
- `mods/machinations` (signals, pistons, steam machines) is written by `tools/mod_machinations.py`; the engine half is `src/signal.c`, one pass a tick over the squares in `World.devices` - which `world_set_at` keeps up, and which is looked for afresh in a world just made or loaded (`world_find_devices`). Things to keep: a block that reads a signal follows what its inputs had the tick *before* (so loops tick over and never hang); anything that writes a layer directly, not through `world_set_at`, must leave `devices_known` false or call `world_find_devices`; a state that must survive saving is a block of its own (`lever_on`, `piston_right_out`), never a number kept on the side - the signal tables are not saved. A thing with a front is four blocks, one a turn of the next, joined by `"turns_to"`, and an item with `"turns"` (the wrench) in hand turns it - a plain click does not: `"use_becomes"` is for what a click works, a lever or a button. A piston's head belongs to its piston: `world_set_at` takes it away when an extended piston goes, and `signal_tick` removes any head with no piston behind it. A block whose picture does not fill its square (a piston's head, a piston that is out) is `"see_through"`, or the faces of the blocks beside it are not drawn. Its belts, arms, hoppers and steam machines are the fields Industry's use (`conveyor`, `extractor`, `sorts`, `automat`, `miner`, `endless`) under names of their own: it does not need Industry on.
- **A mod's items go in the game's own trade categories where they fit, and that is preferred** - but it is not a rule. Where a mod has a kind of thing that is clearly a category of its own (Potioncraft's potions, Discovery Road's relics), make the category in the mod's `trade.json` and sort the items into it as seems right. What was tried and taken back out was a section per MOD, holding everything of the mod's whatever it was: do not do that. Benches, portals and creatures go in `benches`, `portals` and `creatures`, which only the dev portal lists.
- A mod adds to lists the game already has by naming things (tiles, items, trees, mobs, veins, cave decorations) or through the lists made for adding (`"biome_plants"`, `"island_trees"`, recipes). Do not make a mod restate a whole biome to add a plant to it.
- Worlds, crystals and the portal chest belong to the playset in use (`playsets_saves` in `src/mods.c`): playsets are named by the player and listed in `saves/playsets.txt`, and which mods are on is whatever the playset in use says (`playsets_apply`). Removing a playset only takes it off the list - nothing in `saves/` is ever deleted by the game. Anything new that is kept between worlds goes in that directory too, not in `saves/` itself.
- `tests/test_game.c` loads each mod on top of the shipped data (`test_magic_mod`, `test_industry_mod`, `test_digital_mod`, `test_culinary_mod`, `test_explorers_mod`, `test_discovery_mod`, `test_alchemie_mod`, `test_dimensions_mod`, `test_rags_mod`, `test_machinations_mod`, `test_potioncraft_mod`, `test_seeker_mod`, `test_sky_mod`, `test_plunder_mod`) and checks its counts: change them there when a mod's content changes.
- Two mods that define the same name cannot be on together (`mods_conflict`): asked for together, none is loaded. Do not make a mod depend on another being on.

### Still in code, to be moved when touched

- The interface: layouts, wording and colours of the inventory bar, bench menu and menus.
- Default key bindings and their labels (`src/menu.c`).
- The character's poses and how fast they move through them (`draw_player` in `src/main.c`: each frame a pose is worked out from what the character is doing and the drawn one eased toward it, kept per character in `body_ease`; a new pose is a new branch there, never a jump) and the shape of the body (`src/playermodel.c`): the skin and what is worn over it are pictures named in the data. The sky, sun and moon (`src/main.c`).
- The movement rules themselves (walking, hopping, climbing) are code; their timings are data.

## Working here

- Build with `make`, run with `make run`, test with `make test`. In a shell running under Rosetta, prefix with `arch -arm64`.
- The game and the tests read `data/` relative to the directory they are run from: run them from the repository root.
- The recipe book in the pause menu (`src/recipeui.c`) is drawn from `src/guide.c`, which works out from the tables where each item comes from. A new way of getting an item (a new kind of drop, loot or reward) needs a line there, or the book will say the item cannot be got.
- `recipes.txt` is the list the newest batch of recipes was written out from (the earlier batches are in its history); nothing is removed from `data/recipes.json` because it is not in that file. `obtainment.txt` lists what they leave unobtainable or without a use; it is produced from the data, so regenerate or correct it when recipes, drops or world generation change.
- Block ids take two bytes in the world and in saves (there is room for 4,095 kinds of block; 356 are in use by the game itself, and about 1,000 with every mod that can be on together, of which Dimensions is 402). A feature that wants a great many look-alike blocks (a colour, a size) should still keep a number with the block (`World.meta`, as two-tone flowers do) rather than add a block for each.
- The interface carries no explanations: a menu names its controls and nothing else, and what a thing does is said in `README.md`. Check that new text fits where it is drawn at 1280 by 720.
- `tests/legacy/` is a small fixed set of recipes and benches that the tests of how the game works run against, so that changing what the game ships with does not break them. The shipped recipes have a test of their own (`test_shipped_recipes`) which runs first, against `data/` alone. When recipes change, change that test; leave `tests/legacy` alone.
- `tests/test_game.c` is headless and covers the rules. It looks content up by name, and its last test loads a small mod on top of the shipped data. Add a test with each rule change.
- Rendering code (`main.c`, `hud.c`, `benchui.c`, `menu.c`, `assets.c`, `world3d.c`, `playermodel.c`) needs a window and is not covered by tests.
- `third_party/cjson` is vendored; do not edit it.
- There is room for 64 biomes and 128 trees (`MAX_BIOMES`, `MAX_TREES` in `src/content.h`). With Culinary Delights, Explorer's Delight and Dimensions all on, about 46 biomes and 50 trees are in use. There is room for 8 dimensions and for 8 places in one world (`MAX_DIMENSIONS`, `MAX_REGIONS`); a save may be 4,096 rows tall, and a world with all three of Dimensions' places is 1,149.

- **The limits** are the `MAX_*` constants, mostly in `src/content.h` and `src/game.h`. All of them were multiplied by four at version 29. Four are also the sizes of arrays a save holds whole - `MAX_CONTAINERS`, `MAX_DROPS`, `MAX_STORAGES`, `MAX_MOBS` - so changing any of those is a change of save format: the sizes older saves were written with are kept as `V28_*` in `src/save.c`, and every reader of an older version uses those, never the live constant. The table of definitions is static and is about 66 MB now (`sizeof(Content)`); a `Game` is about 470 KB, and tests keep two or three on the stack at once.
- Limits that were deliberately not raised, and why: `INVENTORY_SLOTS`, `BASKET_SLOTS`, `ARMOR_SLOTS`, `CONTAINER_MAX_SLOTS` and `HUD_MAX_EXTRA_SLOTS` (the bar and the menus are laid out for them); `MAX_CHARACTERS` (the buttons down the side, and the rules say how many a world may have); `MAX_TINTS` (a paint is one byte in the world, so 250 is all there can be); `MAX_SEASONS`, `LIGHT_MAX`, `WATER_FULL`, `CELL_TYPES`, `SIGN_TEXT_MAX`, `MAX_CRAFT_AMOUNT` and the tone and paint encodings (rules of the game, not room for things); the lengths of names (`CONTENT_NAME_LEN` is how names are written in saves); and `MAX_TICK_RATE` and `MAX_TICKS_PER_UPDATE` (there so a slow frame cannot snowball). Creature kinds are a byte in saves, so `MAX_MOB_KINDS` (192) cannot pass 255 without a change of format.
